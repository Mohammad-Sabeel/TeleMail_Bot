# TeleMail

A Telegram bot that reads your Gmail, tells you what matters, warns you when a
message lies about who sent it, and can't be talked into touching your mailbox
by anyone who emails you.

It is also an experiment. A language model reads untrusted email, so it can be
prompt-injected. The question is whether the **architecture**, rather than the
model, stops that becoming an action.

## How it works

```
  UNTRUSTED — no execution authority          DETERMINISTIC — holds all authority
 ┌──────────────────────────────────┐      ┌──────────────────────────────────┐
 │  Gmail ──▶ Sync ──▶ Prefilter    │      │   BROKER          Adapter        │
 │  readonly  history   headers +   │      │   schema check    search·get     │
 │            .list     rules       │      │   op allowlist    READ ONLY      │
 │                         │        │      │   audit log            │         │
 │                         ▼        │      │        │               ▼         │
 │                      Planner ────┼──────┼───▶ accepted?  ───▶ Telegram     │
 │                      model       │      │                     allowlisted  │
 └──────────────────────────────────┘      └──────────────────────────────────┘
                                    ▲
                          ENFORCEMENT BOUNDARY
                       validated typed JSON only
```

- **Read-only by token, not by convention.** The OAuth scope is `gmail.readonly`, so
  the credentials themselves can't send, delete or modify mail.
- **The model holds no mailbox client.** It can only *propose* typed JSON. The
  broker validates each proposal against an allowlist, audits it and runs it, or
  rejects it. A test proves the planner can't reach the adapter.
- **Sender checks are computed by code.** SPF, DKIM and DMARC are read from
  Gmail's own `Authentication-Results` (`mx.google.com` only), and they can't be
  overridden by anything a message says.
- **Email bodies are never stored.** Only metadata and snippets are kept; bodies
  are fetched on demand.
- **No specific model is part of the design.** The model is one value,
  `MODEL_NAME` in `.env`, chosen by a probe (`make probe`).

## What it does in Telegram

| | |
|---|---|
| `/sync` | fetch new mail, triage it, read the important non-bulk mail and send a PDF report with a verdict and evidence per email |
| `/expect` | tell it which emails you're waiting for today, and it matches them as they arrive |
| plain messages | questions about your mail, answered with numbered sources and code-computed warnings, including for flagged emails the answer didn't cite |
| `/flag <text>` | add a known-bad phrase, domain or address |
| `/forget` | clear the conversation |

## Research questions

| | Question | Where |
|---|---|---|
| **RQ1** | Does hybrid deterministic-plus-model triage beat either part alone? | `eval/triage_metrics.py` |
| **RQ2** | Does deterministic mediation reduce injection success compared with direct dispatch? | `eval/run_attacks.py`, `eval/run_goals.py` |
| **RQ3** | Does the mediation layer cost anything in quality or latency? | `eval/performance.py` |

Each attack is run through two arms that share one model output: **naive**, where
the proposal is dispatched directly, and **mediated**, where it goes through the
broker. Any difference between them comes from the architecture alone.
Every figure is in [`results.md`](results.md) and is regenerated by
`make evaluate`; none is typed by hand. The design, the threat model, the OWASP LLM
Top 10 mapping and the limitations are in [`docs/BUILD_PLAN.md`](docs/BUILD_PLAN.md).

## Setup

Built and tested on Python 3.14. Needs a Google Cloud OAuth desktop client, a Telegram bot
token and an OpenRouter key.

```bash
python -m venv .venv && .venv/bin/pip install -r requirements-lock.txt
cp .env.example .env                      # fill in; .env is gitignored
# put the Google OAuth client at data/credentials.json
.venv/bin/python -m scripts.check_setup   # what's configured, without printing secrets
make probe MODEL=<openrouter-model-id>    # keep a model scoring >= 14/20, set MODEL_NAME
make sync                                 # first run opens the Google consent screen
make bot
```

## Commands

| | |
|---|---|
| `make test` | full test suite (no network, no model) |
| `make bot` | run the Telegram bot |
| `make sync` / `make status` | one Gmail poll / counts and watermark |
| `make label` | label emails for RQ1 (the system's verdict is hidden while you label) |
| `make evaluate-offline` | results that need no model or labels |
| `make evaluate` | every number in `results.md` |
| `python -m scripts.demo_spoof_alert [--send]` | spoofed email → alert, with no model involved |
| `python -m scripts.test_telegram` | check the Telegram connection on its own |

## Layout

```
telemail/        the bot: sync, prefilter, planner, broker, Gmail adapter, report
  broker/        the enforcement boundary (allowlisted, typed intents)
  gmail/         read-only adapter, OAuth, header parsing
  triage/        prefilter, model planner, assessment, retrieval and answers
eval/            attack harnesses, graders, detectors, metrics, results rendering
scripts/         setup checks, labelling, model probe, corpus harvesting
tests/           pytest suite
data/fixtures*/  attack and control emails; data/*.csv|json are result tables
docs/BUILD_PLAN.md   the plan and the source of truth for every design decision
```

## Known gaps

- **Single user, local process.** The bot answers one allowlisted Telegram chat
  and stops when the machine sleeps.
- **Alerts aren't pushed.** Spoof and urgency alerts (`TeleMailBot.send_alert`,
  with approval buttons bound to a message id) are built and tested, but nothing
  calls them since the background poll was replaced by `/sync`.
- **Most mail is never assessed.** Only `/sync` and full reads during answers
  run the assessment, and bulk mail is skipped, so an answer warning fires only for
  an email that has been flagged.
- **Metadata goes to a third party.** Subjects, snippets and fetched bodies are
  sent to the model provider configured in `.env`.

More are listed in `docs/BUILD_PLAN.md`, in the OWASP table and the limitations.
